# AI Agent Evaluation — Complete Consolidated Guide

## 1. Overview

**AI agent evaluation** is the process of measuring how well an agent reasons, selects and calls tools, and completes tasks—at the scope that matches each failure mode—so you can pinpoint exactly what is broken.

A successful agent outcome depends on both:

1. **Reasoning**
2. **Action**

Because an agent can fail at different points, evaluation should not be treated as a single score. Different evaluation scopes and metrics inspect different parts of the agent's behavior.

---

# 2. The AI Agent Architecture

An AI agent can be viewed as two interacting layers:

```text
                    USER TASK
                        |
                        v
              +-------------------+
              |  Reasoning Layer   |
              |       LLM          |
              |-------------------|
              | Understand task    |
              | Create plan        |
              | Decide next step   |
              | Select tools       |
              +---------+---------+
                        |
                        v
              +-------------------+
              |    Action Layer    |
              |   Tools / APIs     |
              |-------------------|
              | Call tools         |
              | Pass arguments     |
              | Execute actions    |
              +---------+---------+
                        |
                        v
                   Observation
                        |
                        v
                 Reasoning again
                        |
                        v
                  Final Outcome
```

The reasoning and action layers form a loop:

```text
Task
  ↓
Reason
  ↓
Choose Action
  ↓
Call Tool
  ↓
Observe Result
  ↓
Reason Again
  ↓
Choose Next Action
  ↓
...
  ↓
Final Result
```

---

# 3. Three Complementary Evaluation Scopes

AI agent evaluation uses three major scopes.

| Scope | What it evaluates | Main question |
|---|---|---|
| **End-to-End / Black-Box** | Observable input and final output | Did the agent produce the desired result? |
| **Trajectory-Based** | Complete ordered execution trace | How did the agent reach the result? |
| **Component-Level / Step-Wise** | One span or decision in isolation | Was this particular decision correct? |

## 3.1 End-to-End / Black-Box Evaluation

End-to-end evaluation treats the agent as a black box.

```text
Input
  ↓
Agent
  ↓
Final Output
```

The internal execution is not inspected.

### Best used for

- Overall behavior
- Final answer quality
- Final task success
- High-level regression testing

### Limitation

If the final result is wrong, end-to-end evaluation may tell you **that it failed**, but not necessarily **where it failed**.

---

## 3.2 Trajectory-Based Evaluation

Trajectory-based evaluation examines the complete ordered execution trace.

A trajectory can contain:

```text
User Task
↓
Reasoning / Plan
↓
LLM Call
↓
Tool Call
↓
Tool Arguments
↓
Tool Output / Observation
↓
Next LLM Call
↓
Next Tool Call
↓
...
↓
Final Output
```

### Best used for

- Planning
- Plan adherence
- Task completion
- Step efficiency
- Understanding why an agent failed

Trajectory-based metrics require tracing because they inspect the complete ordered execution.

---

## 3.3 Component-Level / Step-Wise Evaluation

Component-level evaluation focuses on one specific span or decision.

For example:

```text
Agent
 ├── LLM Span            ← evaluate tool selection here
 ├── Tool Span
 ├── Retrieval Span
 └── Final Output
```

### Best used for

- Tool selection
- Tool arguments
- Individual LLM decisions
- Specific agent components

The important principle is:

> Evaluate each failure mode at the scope where the relevant information is visible.

---

# 4. Reasoning Layer

The **reasoning layer** contains the LLM.

Its responsibilities include:

- Understanding the user task
- Creating a plan
- Deciding what should happen next
- Selecting tools
- Adapting to observations

The supplied evaluation framework identifies two trajectory metrics for reasoning and planning:

- `PlanQualityMetric`
- `PlanAdherenceMetric`

---

# 5. Plan Quality

## 5.1 What is Plan Quality?

`PlanQualityMetric` evaluates whether the plan generated by the agent is logical, complete, and aligned with the task.

The important question is:

> **Is the strategy itself good?**

A plan can be evaluated independently from whether the agent follows it.

---

## 5.2 How Plan Quality Is Calculated

The supplied description explains the process as:

### Step 1 — Extract the Task

The task is extracted from the trace.

The task represents the user's goal or intent and should be actionable.

### Step 2 — Extract the Plan

The plan is extracted from the agent's `thinking` or `reasoning`.

If there are no statements that clearly define or imply a plan in the trace, the supplied description states that the metric passes by default with a score of `1`.

### Step 3 — Calculate Alignment

Conceptually:

```text
Plan Quality Score
=
AlignmentScore(Task, Plan)
```

The alignment score uses an LLM to generate the final score from the task and extracted plan.

---

## 5.3 Example

### User Task

> Find AI/ML Engineer jobs in Hyderabad.

### Good Plan

```text
1. Understand role = AI/ML Engineer
2. Understand location = Hyderabad
3. Search relevant jobs
4. Filter results by location
5. Rank relevant jobs
6. Return recommendations
```

### Poor Plan

```text
1. Search jobs
2. Generate a cover letter
3. Search unrelated information
4. Search jobs again
5. Return results
```

The second plan contains unnecessary actions and is poorly aligned with the actual task.

---

# 6. Plan Adherence

## 6.1 What is Plan Adherence?

`PlanAdherenceMetric` evaluates whether the agent follows its own plan during execution.

The important question is:

> **Did the agent actually execute the strategy it planned?**

An agent can have:

- A good plan but poor adherence
- A poor plan but strong adherence

Therefore, Plan Quality and Plan Adherence are different metrics.

---

## 6.2 How Plan Adherence Is Calculated

The supplied description explains:

### Step 1 — Extract the Task

The user's task is extracted from the trace.

### Step 2 — Extract the Plan

The plan is extracted from the trace's reasoning/thinking.

### Step 3 — Evaluate Execution Steps

The actual execution steps are compared against the task and plan.

Conceptually:

```text
Plan Adherence Score
=
AlignmentScore((Task, Plan), Execution Steps)
```

The final alignment score is generated using an LLM.

---

## 6.3 Example

### Plan

```text
Search jobs
    ↓
Filter Hyderabad
    ↓
Rank jobs
    ↓
Return results
```

### Actual Execution

```text
Search jobs
    ↓
Filter Hyderabad
    ↓
Search unrelated web information
    ↓
Generate a cover letter
    ↓
Rank jobs
    ↓
Return results
```

The agent deviated from its planned strategy.

---

# 7. Plan Quality vs Plan Adherence

| Situation | Plan Quality | Plan Adherence | Meaning |
|---|---:|---:|---|
| Good plan + followed | High | High | Ideal |
| Bad plan + followed | Low | High | Strategy is poor, execution is consistent |
| Good plan + not followed | High | Low | Strategy is good, execution deviated |
| Bad plan + not followed | Low | Low | Both planning and execution need improvement |

This distinction is useful when diagnosing whether a problem is in:

- The reasoning strategy
- The execution/control logic

---

# 8. Action Layer

The **action layer** contains tools such as:

- Function calls
- APIs
- Search tools
- Retrievers
- Databases
- External services
- Browser tools
- Other executable actions

The action layer is primarily evaluated using:

- `ToolCorrectnessMetric`
- `ArgumentCorrectnessMetric`

---

# 9. Tool Correctness

## 9.1 What is Tool Correctness?

`ToolCorrectnessMetric` evaluates an LLM agent's function/tool calling ability.

It checks whether:

1. The tools that were expected to be used were actually called.
2. The tools selected by the agent were appropriate/optimal for the task.

The supplied documentation describes this as an agentic LLM metric.

---

## 9.2 Required Test Case Fields

To use `ToolCorrectnessMetric`, the test case requires:

- `input`
- `actual_output`
- `tools_called`
- `expected_tools`

Conceptually:

```text
Input
  +
Actual Output
  +
Tools Called
  +
Expected Tools
```

---

## 9.3 Example

```python
from deepeval.test_case import LLMTestCase, ToolCall
from deepeval.metrics import ToolCorrectnessMetric
from deepeval import evaluate

test_case = LLMTestCase(
    input="What if these shoes don't fit?",
    actual_output="We offer a 30-day full refund at no extra cost.",
    tools_called=[
        ToolCall(name="WebSearch"),
        ToolCall(name="ToolQuery")
    ],
    expected_tools=[
        ToolCall(name="WebSearch")
    ]
)

metric = ToolCorrectnessMetric()

evaluate(
    test_cases=[test_case],
    metrics=[metric]
)
```

---

# 10. Tool Correctness Configuration

The supplied documentation describes several optional controls.

## `available_tools`

A list of tools that were available to the LLM agent.

It provides context for evaluating tool-selection optimality.

---

## `threshold`

Minimum passing threshold.

The supplied default is:

```text
0.5
```

It can also be set to `None` for score-only mode.

---

## `evaluation_params`

Controls how strict correctness should be.

The supplied options include:

- `ToolCallParams.INPUT_PARAMETERS`
- `ToolCallParams.OUTPUT`

This allows evaluation beyond just matching the tool name.

---

## `include_reason`

Controls whether an evaluation reason is included.

Default:

```text
True
```

---

## `strict_mode`

When enabled:

```text
1 = perfect
0 = otherwise
```

It also overrides the threshold and sets it to `1`.

---

## `verbose_mode`

When enabled, intermediate calculation steps are printed.

---

## `should_consider_ordering`

When enabled, the order of tool calls is considered.

For example:

```text
Expected:
WebSearch
ToolQuery
WebSearch
```

versus:

```text
Actual:
WebSearch
WebSearch
ToolQuery
```

If ordering is enabled, the sequence matters.

---

## `should_exact_match`

When enabled, `tools_called` and `expected_tools` must match exactly.

It is stricter than ordering and overrides the effect of `should_consider_ordering`.

---

# 11. Tool Correctness Calculation

The supplied documentation describes a deterministic score based on tool usage.

Conceptually:

```text
Tool Correctness
=
Correctly Used Tools
/
Total Tools Called
```

More specifically, correctness can consider:

- Tool names
- Input parameters, if configured
- Outputs, if configured
- Ordering
- Exact matching

---

## 11.1 Deterministic + Model-Based Evaluation

The supplied documentation states that Tool Correctness is different from most metrics because it can combine deterministic and non-deterministic evaluation.

### Step 1 — Deterministic Evaluation

Compare:

```text
tools_called
vs
expected_tools
```

### Step 2 — Optional Optimality Evaluation

If `available_tools` is supplied, an LLM evaluates whether the selected tools were the most optimal for the task.

### Final Score

The supplied description states that the final score is the **minimum** of:

```text
Deterministic Score
LLM-Based Optimality Score
```

If `available_tools` is not supplied, the additional model-based optimality evaluation does not occur.

---

# 12. Tool Correctness Evaluation Modes

The supplied material documents three modes:

```text
llm
hybrid
system_one
```

### LLM Mode

The LLM evaluates the relevant model-based selection judgment.

This is the default mode in the supplied documentation.

### Hybrid Mode

- LLM extracts information
- Jev / System One evaluates the tool-selection judgment

If the Jev call fails, the LLM can perform the decision instead.

### System One Mode

Jev evaluates the tool-selection judgment without an LLM judge.

---

# 13. Tool Correctness Within Components

`ToolCorrectnessMetric` can also be used for component-level evaluation.

A component can be observed and the metric attached to that span.

Conceptually:

```python
@observe(metrics=[metric])
def inner_component():
    ...
```

The test case can then be created at runtime and attached to the current span.

This is useful when the goal is specifically to evaluate an LLM component responsible for tool selection.

---

# 14. Tool Correctness vs Argument Correctness

These metrics solve different problems.

| Metric | Question |
|---|---|
| **Tool Correctness** | Did the agent choose the right tool? |
| **Argument Correctness** | Did the agent provide correct arguments to the tool? |

Example:

```text
Task:
Find AI/ML Engineer jobs in Hyderabad.

Selected Tool:
LinkedInJobSearch
```

The tool selection can be correct.

But:

```json
{
  "role": "Data Scientist",
  "location": "Delhi"
}
```

can still be incorrect.

Therefore:

```text
Tool Correctness      → High
Argument Correctness  → Low
```

This distinction is one of the most important concepts in agent evaluation.

---

# 15. Argument Correctness

## 15.1 What is Argument Correctness?

`ArgumentCorrectnessMetric` evaluates whether the arguments generated for each tool call are correct based on the input/task.

It is:

- LLM-judged
- Referenceless

The supplied documentation explicitly notes that deterministic argument evaluation can instead be done using Tool Correctness with input-parameter matching.

---

## 15.2 Required Test Case Fields

The required fields are:

- `input`
- `actual_output`
- `tools_called`

Unlike Tool Correctness, an `expected_tools` list is not required.

---

## 15.3 Example

```python
from deepeval.metrics import ArgumentCorrectnessMetric
from deepeval.test_case import LLMTestCase, ToolCall
from deepeval import evaluate

metric = ArgumentCorrectnessMetric(
    threshold=0.7,
    model="gpt-4",
    include_reason=True
)

test_case = LLMTestCase(
    input="When did Trump first raise tariffs?",
    actual_output="Trump first raised tariffs in 2018 during the U.S.-China trade war.",
    tools_called=[
        ToolCall(
            name="WebSearch Tool",
            description="Tool to search for information on the web.",
            input={
                "search_query": "Trump first raised tariffs year"
            }
        ),
        ToolCall(
            name="History FunFact Tool",
            description="Tool to provide a fun fact about the topic.",
            input={
                "topic": "Trump tariffs"
            }
        )
    ]
)

evaluate(
    test_cases=[test_case],
    metrics=[metric]
)
```

---

# 16. Argument Correctness Calculation

The supplied documentation gives the conceptual equation:

```text
Argument Correctness
=
Correctly Generated Input Parameters
/
Total Number of Tool Calls
```

The LLM determines whether each tool-call argument correctly addresses the input/task.

---

- `threshold`
- `model`
- `include_reason`
- `strict_mode`
- `async_mode`
- `verbose_mode`
- `flaky`
- `system_one_model`
- `eval_mode`

### Default threshold


### Strict mode

With `strict_mode=True`:

```text

```

### Custom evaluator model

The `model` can specify the LLM used for the evaluation, including a supported custom model type.

# 18. Argument Correctness Within Components

Argument Correctness can be attached to a nested component using tracing.

Conceptually:

```python
@observe(metrics=[metric])
def inner_component():
    test_case = LLMTestCase(
        input="...",
        actual_output="...",
        tools_called=[...]
    )

    update_current_span(
        test_case=test_case
    )
```

This makes it possible to evaluate the component responsible for generating tool calls and their arguments.

---

# 19. Argument Correctness Evaluation Modes

The supplied documentation also describes:

```text
llm
hybrid
system_one
```

### LLM Mode

The LLM evaluates argument correctness.

### Hybrid Mode

Jev / System One can evaluate individual tool-call argument correctness.

The supplied description says the assessment can become a yes/no judgment for each tool call, with:

```text
P(yes) >= 0.5
```

counted as correct.

### System One Mode

Jev evaluates the complete metric using the structured tool-call information.

The supplied documentation describes three questions covering:

1. Whether every tool call has arguments that correctly address the task
2. Whether any tool call contains missing, irrelevant, or wrong arguments
3. How many tool calls have correctly addressed arguments

These answers are converted into values in `[0, 1]` and combined using a weighted mean.

---

# 20. Overall Execution Evaluation

Once tool usage and reasoning are evaluated, the complete execution can be evaluated using:

- `TaskCompletionMetric`
- `StepEfficiencyMetric`

These are trajectory-level metrics.

---

# 21. Task Completion

## 21.1 What is Task Completion?

`TaskCompletionMetric` evaluates how effectively an LLM agent accomplishes a task.

It analyzes the agent's full trace to determine whether the intended task was successfully completed.

The supplied documentation explicitly states:

> Task Completion analyzes the agent's full trace to determine task success.

Therefore, tracing is required for trajectory-based use.

---

# 22. Task Completion Usage

The supplied example uses:

```python
from deepeval.dataset import Golden, EvaluationDataset
from deepeval.metrics import TaskCompletionMetric
from deepeval.tracing import observe

@observe()
def trip_planner_agent(input):
    ...

dataset = EvaluationDataset(
    goldens=[
        Golden(input="This is a test query")
    ]
)

task_completion = TaskCompletionMetric(
    threshold=0.7,
    model="gpt-4o"
)

for golden in dataset.evals_iterator(
    metrics=[task_completion]
):
    trip_planner_agent(golden.input)
```

---

# 23. Task Completion Parameters

The supplied material describes parameters including:

- `threshold`
- `task`
- `model`
- `include_reason`
- `strict_mode`
- `async_mode`
- `verbose_mode`
- `flaky`
- `system_one_model`
- `eval_mode`

### `task`

The task can optionally be supplied directly.

If it is not supplied:

```text
task = None
```

the task is inferred from the trace.

---

# 24. Task Completion Calculation

The supplied equation is:

```text
Task Completion Score
=
AlignmentScore(Task, Outcome)
```

### Step 1

Extract:

```text
Task
Outcome
```

from the trace.

### Step 2

Calculate how well the outcome aligns with the task.

The alignment score is generated by an LLM in LLM-as-a-judge mode.

---

# 25. Task Completion Example

### User Task

> Find three AI/ML jobs in Hyderabad.

### Successful run

```text
Understand request
↓
Search jobs
↓
Find 3 relevant jobs
↓
Return them
```

Result:

```text
Task Completion → High
```

### Partial run

```text
Understand request
↓
Search jobs
↓
Find jobs
↓
Stop without returning them
```

Result:

```text
Task Completion → Low / Partial
```

---

# 26. Task Completion vs Plan Adherence

These answer different questions.

| Metric | Question |
|---|---|
| **Task Completion** | Did the agent accomplish the task? |
| **Plan Adherence** | Did the agent follow its own plan? |

An agent can:

```text
Follow its plan but fail the task
```

or:

```text
Ignore its plan but still complete the task
```

Therefore, these metrics should not be treated as interchangeable.

---

# 27. Task Completion Evaluation Modes

The supplied documentation describes:

```text
llm
hybrid
system_one
```

### LLM

LLM extracts task/outcome and judges alignment.

### Hybrid

- LLM extracts task/outcome
- Jev provides the alignment score

### System One

Jev evaluates the trace directly.

The supplied documentation describes structured questions concerning:

1. Whether the run fully accomplishes the user's task
2. Whether the final outcome matches the requested task
3. How completely the task was accomplished

These values are combined into a weighted mean.

# 28. Step Efficiency

## 28.1 What is Step Efficiency?

`StepEfficiencyMetric` evaluates how efficiently the agent executes a task.

It analyzes the full trace to determine:

- What the task was
- What execution steps occurred
- Whether those steps were necessary
- Whether the route contained unnecessary actions

The supplied material explicitly states that Step Efficiency is a trace-only metric.

It must be used through:

- `evals_iterator`
- or `observe`

It cannot be used as a standalone metric.

---

# 29. Step Efficiency Usage

The supplied example uses:

```python
from deepeval.tracing import observe, update_current_trace
from deepeval.dataset import Golden, EvaluationDataset
from deepeval.metrics import StepEfficiencyMetric
from deepeval.test_case import ToolCall

@observe
def tool_call(input):
    ...

@observe
def agent(input):
    tools = tool_call(input)
    output = llm(input, tools)

    update_current_trace(
        input=input,
        output=output,
        tools_called=tools
    )

    return output

dataset = EvaluationDataset(
    goldens=[
        Golden(
            input="What's the weather like in SF?"
        )
    ]
)

metric = StepEfficiencyMetric(
    threshold=0.7,
    model="gpt-4o"
)

for golden in dataset.evals_iterator(
    metrics=[metric]
):
    agent(golden.input)
```

---

# 30. Step Efficiency Calculation

The supplied description explains:

### Step 1 — Extract the Task

The task is extracted from the trace.

### Step 2 — Evaluate Execution Steps

The agent's execution steps are evaluated for efficiency.

Conceptually:

```text
Step Efficiency Score
=
AlignmentScore(Task, Execution Steps)
```

The metric penalizes actions that are not strictly required to complete the task.

Examples include:

- Duplicate actions
- Repeated searches
- Unnecessary retrieval
- Detours
- Loops
- Speculative actions

---

# 31. Efficient vs Inefficient Execution

## Efficient

```text
Search
↓
Filter
↓
Rank
↓
Return
```

## Inefficient

```text
Search
↓
Search again
↓
Search again
↓
Retrieve unnecessary information
↓
Search again
↓
Filter
↓
Rank
↓
Return
```

Both could potentially produce a correct final answer.

But:

```text
Task Completion
```

could be high for both, while:

```text
Step Efficiency
```

would be lower for the second.

---

# 32. Task Completion vs Step Efficiency

This distinction is critical.

| Run | Task Completion | Step Efficiency |
|---|---:|---:|
| Fast and successful | High | High |
| Slow/bloated but successful | High | Low |
| Efficient but unsuccessful | Low | High |
| Inefficient and unsuccessful | Low | Low |

### Key principle

> Task Completion evaluates the **outcome**.

> Step Efficiency evaluates the **path**.

The supplied documentation recommends evaluating both because one does not guarantee the other.

---

# 33. Step Efficiency Evaluation Modes

The supplied documentation describes:

```text
llm
hybrid
system_one
```

### LLM

The LLM extracts the task and evaluates execution efficiency.

### Hybrid

- LLM extracts task information
- Jev evaluates efficiency

### System One

Jev directly evaluates the trace and considers:

1. Whether every step was strictly necessary
2. Whether the path was direct
3. Overall efficiency based on the number/directness of steps

# 35. Complete Metric Matrix

| Metric | Layer | Scope | Main Question | Trace Required? |
|---|---|---|---|---|
| `PlanQualityMetric` | Reasoning | Trajectory | Is the plan good? | Yes / trajectory |
| `PlanAdherenceMetric` | Reasoning | Trajectory | Was the plan followed? | Yes / trajectory |
| `ToolCorrectnessMetric` | Action / LLM decision | Component or E2E | Was the right tool selected? | Trace for component-level |
| `ArgumentCorrectnessMetric` | Action / LLM decision | Component or E2E | Were the arguments correct? | Trace optional for component-level |
| `TaskCompletionMetric` | Overall execution | Trajectory | Was the task completed? | Yes |
| `StepEfficiencyMetric` | Overall execution | Trajectory | Was the path efficient? | Yes |

# 36. Dataset-Based Evaluation

A repeatable evaluation system should use an evaluation dataset.

The supplied examples use:

```text
EvaluationDataset
+
Golden
```

Conceptually:

```python
dataset = EvaluationDataset(
    goldens=[
        Golden(input="Task 1"),
        Golden(input="Task 2"),
        Golden(input="Task 3")

)
```

Then the agent is run against the dataset.

---

# 38. Why a Dataset Matters

A dataset makes evaluation repeatable.

Without a dataset:

```text
Change code
↓
Try a few examples manually
↓
Assume improvement
```

With a dataset:

```text
Baseline
↓
Run dataset
↓
Record scores
↓
Change system
↓
Run same dataset
↓
Compare scores
```

This enables regression testing.

# 39. Recommended Evaluation Workflow

## Step 1 — Create Evaluation Cases

Prepare realistic tasks.

Include:

- Normal cases
- Edge cases
- Ambiguous cases
- Tool-selection cases
- Failure-prone cases

---

## Step 2 — Run the Real Agent

Run the actual production-like agent.

Do not rely only on manually constructed hypothetical traces when measuring real behavior.

---

## Step 3 — Capture the Trace

Capture:

```text
User Input
↓
Agent Span
↓
LLM Span
↓
Plan / Reasoning
↓
Tool Call
↓
Tool Arguments
↓
Tool Result
↓
Next LLM Call
↓
Next Tool Call
↓
Final Output
```

---

## Step 4 — Evaluate Planning

Use:

```text
Plan Quality
Plan Adherence
```

---

## Step 5 — Evaluate Tool Selection

Use:

```text
Tool Correctness
```

---

## Step 6 — Evaluate Tool Arguments

Use:

```text
Argument Correctness
```

---

## Step 7 — Evaluate Final Outcome

Use:

```text
Task Completion
```

---

## Step 8 — Evaluate Execution Efficiency

Use:

```text
Step Efficiency
```

---

## Step 9 — Diagnose the Failure

Map the low metric back to the responsible part of the system.

---

## Step 10 — Fix and Re-Evaluate

Potential areas to change:

- System prompt

# 45. Evaluation Modes

```text
llm
```

## 45.1 LLM-as-a-Judge

The LLM evaluates the relevant criterion.

Example:

```bash
deepeval set-eval-mode llm
```

This is described as the default mode in the supplied documentation.

---

## 45.2 Hybrid

The LLM performs extraction while Jev / System One performs the scoring decision.

```bash
deepeval set-eval-mode hybrid
```

This approach is used in the supplied metric documentation for several of the metrics.

---

## 45.3 System One / Jev-as-a-Judge

Jev performs the evaluation without an LLM judge.

```bash
deepeval set-eval-mode system_one
```

The supplied documentation notes that scoring procedures differ between evaluation modes, so when comparing scores across runs, it is important to keep the evaluation mode consistent.

# 46. Thresholds

Many DeepEval metrics use a threshold to determine whether a score passes.

Conceptually:

```text
Score >= Threshold
        ↓
      Pass
```

```text
Score < Threshold
        ↓
      Fail
```

The supplied metric pages commonly show:

```text
threshold = 0.5
```

as the default for several metrics.

Examples in the supplied documentation also use:

```text
threshold = 0.7
```

for stricter examples.

Thresholds should therefore be chosen deliberately for the application's requirements.

---

# 47. Score-Only Mode

The supplied documentation notes that some thresholds can be set to:

```text
None
```

to run the metric in score-only mode.

This is useful when the goal is to observe metric values rather than convert them into pass/fail decisions.

---

# 48. Strict Mode

When `strict_mode=True`, the supplied metric documentation describes a binary interpretation:

```text
1 = perfect
0 = not perfect
```

Strict mode also overrides the threshold and sets it to `1`.

---

# 49. Include Reason

When available,:

```text
include_reason=True
```

provides an explanation for the score.

Reasons are valuable during debugging because the score tells you **how much** the agent succeeded, while the reason can explain **why**.

---

# 50. Verbose Mode

When:

```text
verbose_mode=True
```

the supplied metric documentation states that intermediate calculation steps can be printed.

This is particularly useful when debugging unexpected scores.

# 64. Final Summary

AI agent evaluation should be treated as a **diagnostic system**, not just a final-score system.

The key mapping is:

```text
Reasoning
   |
   +-- Plan Quality
   |
   +-- Plan Adherence

Action
   |
   +-- Tool Correctness
   |
   +-- Argument Correctness

Overall Execution
   |
   +-- Step Efficiency
   |
   +-- Task Completion
```

The main idea is:

> **Evaluate the part of the agent responsible for the failure.**

If the plan is poor, evaluate planning.

If the wrong tool is selected, evaluate tool correctness.

If the right tool receives incorrect parameters, evaluate argument correctness.

If the agent takes unnecessary actions, evaluate step efficiency.

If the user’s actual goal is not achieved, evaluate task completion.

For a complete understanding of an AI agent, use multiple complementary metrics rather than relying on one score.
